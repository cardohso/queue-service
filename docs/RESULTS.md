## 1. asyncio vs threads vs processes

Source: `uv run python -m bench.executors` -> `results/bench/executors.json`. Each cell is the **median of 5 runs with [min-max]**; every run is a 2 s window with W jobs in flight. I/O job = 20 ms wait; CPU job = 32256 sha256 iterations (calibration target 10 ms; **measured: 10.4 ms** per job on one core). asyncio runs the CPU job *inline on the event loop* (no offload), which is what is being measured.

- CPU: Apple M1 Pro, 8 logical (6 performance + 2 efficiency)
- Memory: 16 GB
- OS: Darwin 27.2.0 (macOS 27.2.1)
- Python: CPython 3.14.8, GIL enabled
- Machine load average at start (1/5/15 min): 6.8 / 6.5 / 6.5 on 8 cores
- **Not a quiet machine:** the benchmark waits up to 150 s for the 1-minute load to fall under 4.8 and this run never got there (other applications were using several cores). Parallel-scaling numbers are therefore pessimistic and the spreads wider than on an idle box. Rerun with `scripts/run_benchmarks.sh bench` after closing heavy applications.

### The GIL effect, in numbers (speedup of W=8 over W=1, same mode)

| mode | I/O-bound | CPU-bound |
|---|---|---|
| asyncio | 8.00x | 1.02x |
| threads | 7.99x | 1.00x |
| processes | 8.12x | 3.43x |

With CPU-bound jobs, 8 threads do 1.00x the work of 1 thread (the GIL lets one thread run Python at a time), while their per-job p99 latency grows from 10.0 ms to 295.0 ms as they take turns. 8 processes do 3.43x. A CPU job run inline on the asyncio event loop blocks it: the median of the largest event-loop stall seen in a run was 233 ms at W=8.

## 2. The real system: capacity vs number of worker processes

Source: `uv run python -m bench.e2e` -> `results/bench/e2e.json`. Real Postgres 17 and Redis 8 in containers, real `qs worker` processes (each with up to 32 jobs in flight and 1 CPU child process), fenced commit and ack for every job. A backlog is pre-loaded so the API is not the bottleneck; throughput is measured from the first claim to the last commit. Median of 3 runs with [min-max]. Latency is per attempt, claim to committed (service latency including real Postgres round trips), not end-to-end from submission (a pre-loaded backlog would only measure the backlog).

- CPU: Apple M1 Pro, 8 logical (6 performance + 2 efficiency)
- Memory: 16 GB
- OS: Darwin 27.2.0 (macOS 27.2.1)
- Python: CPython 3.14.8, GIL enabled
- Machine load average at start (1/5/15 min): 9.5 / 6.9 / 6.6 on 8 cores
- **Not a quiet machine:** the benchmark waits up to 150 s for the 1-minute load to fall under 4.8 and this run never got there (other applications were using several cores). Parallel-scaling numbers are therefore pessimistic and the spreads wider than on an idle box. Rerun with `scripts/run_benchmarks.sh bench` after closing heavy applications.

Attempt latency (p50 314 ms for a 10 ms job) is mostly **queueing inside the worker**: up to 32 CPU jobs are in flight but each worker has 1 CPU child process, so they wait for it, and the job timeout and lease clock run while they wait. This is a known design gap (DESIGN.md promised a separate CPU limit); see README known limits.
